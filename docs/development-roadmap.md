# MalMoi Development Roadmap

본 문서는 MalMoi의 개발 기준 로드맵입니다.  
목적은 현재 상태와 다음 우선순위, 최종 목표를 한눈에 보는 것입니다.

- 현재 운영 방식: **A (예약 중심)**
- 중간 확장: **B (예약 + 코스 보조)**
- 최종 목표: **C (혼합형: 예약 + 코스 중심)**
- 개발 환경: **교실 맥미니**
- 외부 테스트 환경: **28 서버 (스테이징)**
- 최종 운영 도메인: **portal.hanguru.school**
- **인증·연락**: 이메일·전화·학생번호·비밀번호 기준 (외부 메신저/LINE 연동 없음)
- **알림**: 메일 발송 + 포털 내 공지·이력·상태 화면을 기본 경로로 사용

---

## 1) 로드맵 기본 원칙

- 기능을 무작정 늘리기보다, **테스트 가능한 운영 흐름**을 먼저 고정한다.
- A를 버리지 않고, A 위에 B를 얹고, B 위에 C를 얹는 방식으로 확장한다.
- 각 Phase는 목표/완료 기준/다음 조건이 명확해야 한다.

---

## 2) 현재 위치 (Current State)

현재 MalMoi는 **Phase 1~2 사이(학생 운영 MVP + 관리자 운영 안정화 진행 중)** 입니다.

근거:
- 학생 등록/로그인/비밀번호 재설정/강제 비밀번호 변경 흐름 구현
- 학생/관리자 핵심 예약 운영 및 기본 권한 구조 구현
- 보호자 읽기 중심 구조 구현
- SMTP 실제 발송 기반 검증 가능 상태 확보

---

## 3) A -> B -> C 확장 흐름

## A 단계: 예약 중심 운영
- 학생은 예약 중심으로 학습을 진행
- 관리자는 예약/학생/공지/기본 정책 운영
- 핵심 가치: 빠른 운영 시작, 낮은 복잡도

## B 단계: 예약 + 코스 보조
- 예약 중심은 유지
- 코스/학습목표 태그를 보조 레이어로 도입
- 예: TOPIK 준비, 회화 집중, 60/90분 추천 흐름
- 핵심 가치: 학습 맥락 추가, 운영 부담 최소화

## C 단계: 혼합형 (예약 + 코스 중심)
- 학생은 계속 자유 예약 가능
- 교실은 코스 흐름(진도/출석/숙제/평가/결제)도 함께 관리
- 핵심 가치: 예약의 유연성과 코스의 체계성을 동시에 확보

## 5) Phase 로드맵

## Phase 0 - 기반 정리 / 외부 테스트 준비
- 목표
  - 개발/스테이징 운영 루틴 고정
- 왜 필요한가
  - 기능보다 먼저 운영 실패를 줄여야 함
- 포함 기능/작업
  - 맥미니(개발) / 28(스테이징) 역할 분리
  - 문서/체크리스트 정리
  - SMTP/도메인/HTTPS 기초 점검
- 완료 기준
  - 문서화 + 점검 루틴 실행 가능
- 다음 조건
  - 학생 운영 MVP를 외부 테스트할 준비 완료

## Phase 1 - 학생 운영 MVP
- 목표
  - 학생이 등록/로그인/예약/기본 조회를 수행 가능
- 왜 필요한가
  - 실제 사용자 흐름의 최소 단위
- 포함 기능
  - 등록 시작 -> 메일 인증 -> 동의 -> 개인정보 -> 완료
  - 로그인(ID/PW), 비밀번호 재설정, 첫 로그인 변경
  - 학생 예약/공지/개인정보
- 완료 기준
  - 학생 단독 E2E 시나리오 성공
- 다음 조건
  - 관리자 운영과 충돌 없이 연동 가능

## Phase 2 - 관리자 운영 안정화
- 목표
  - 운영자가 학생/예약/공지/정책을 안정적으로 관리
- 왜 필요한가
  - 베타 운영 중 장애/예외 대응의 중심
- 포함 기능
  - 학생 관리, 예약 운영, 공지 관리, 정책 관리, 감사 로그
  - 페어 관계/페어 예약 운영
- 완료 기준
  - 주요 운영 시나리오에서 수작업 복구 최소화
- 다음 조건
  - 보호자/교사 확장을 수용할 구조 확보

## Phase 3 - 보호자 기능 실제화
- 목표
  - 보호자 읽기 중심 동선을 실사용 가능 수준으로 정리
- 왜 필요한가
  - 미성년 학생 운영 품질 향상
- 포함 기능
  - 자녀 조회, 예약/공지/레슨노트/숙제(권한 기반) 조회
  - 보호자 권한 플래그 정교화
- 완료 기준
  - 보호자 계정으로 기본 조회 흐름 안정
- 다음 조건
  - 교사 운영 화면과 데이터 연결 강화

## Phase 4 - 교사 기능 안정화
- 목표
  - 교사가 담당 수업 운영을 독립적으로 수행
- 왜 필요한가
  - 관리자 의존도를 낮추고 수업 품질 높임
- 포함 기능
  - 레슨노트 작성/수정 권한
  - 담당 수업 확인/처리
- 완료 기준
  - 교사 동선에서 일상 운영 가능
- 다음 조건
  - 출석/숙제 기능 접합 준비

## Phase 5 - 출석 시스템
- 목표
  - 예약 결과를 출석 데이터로 명확히 확정
- 왜 필요한가
  - 진도/정산/통계의 기반 데이터
- 포함 기능
  - 출석 상태 확정, 변경 이력, 운영 예외 처리
- 완료 기준
  - 출석 확정 데이터의 신뢰성 확보
- 다음 조건
  - 숙제/레슨노트/통계와 연동 가능

## Phase 6 - 숙제 시스템
- 목표
  - 수업 후 학습 루프(제시 -> 수행 -> 피드백) 정착
- 왜 필요한가
  - 학습 지속성과 성과 추적 강화
- 포함 기능
  - 숙제 등록/조회/완료/피드백
  - 학생/보호자/교사 화면 연결
- 완료 기준
  - 최소 1주기 운영 루프 안정
- 다음 조건
  - 포인트/시간/패키지 정책 연계 가능

## Phase 7 - 포인트/시간/패키지 정리
- 목표
  - 결제 전 단계의 자원 체계를 운영 가능한 형태로 정리
- 왜 필요한가
  - 향후 결제 시스템 도입의 기반
- 포함 기능
  - 포인트/시간 정책 고정
  - 패키지 모델 정리
- 완료 기준
  - 운영자가 규칙 변경/예외 처리 가능
- 다음 조건
  - 코스 보조 도입(B) 시 충돌 없음

## Phase 8 - 코스 보조 도입 (B 단계)
- 목표
  - 예약 중심에 코스 맥락을 보조 레이어로 연결
- 왜 필요한가
  - 학습 방향성과 추천 흐름 제공
- 포함 기능
  - 코스/목표 태그
  - 레슨노트/숙제와 코스 맥락 연결
- 완료 기준
  - 예약 운영을 해치지 않고 코스 맥락 제공
- 다음 조건
  - 혼합형 구조(C) 진입 판단 가능

## Phase 9 - 혼합형 구조 진입 (C 단계)
- 목표
  - 예약 + 코스 중심 운영을 동시에 수행
- 왜 필요한가
  - 유연성과 체계성의 균형 확보
- 포함 기능
  - 진행도 관리
  - 결제/패키지 연결
  - 통계 대시보드
- 완료 기준
  - 학생/보호자/교사/관리자 전체 동선에서 혼합형 운영 가능
- 다음 조건
  - 정식 공개 및 장기 운영 전환

## 5-1) Phase별 예상 기간 (권장)

아래 기간은 권장 범위이며, 외부 테스트 결과에 따라 조정합니다.

| Phase | 권장 기간 | 비고 |
|---|---:|---|
| Phase 0 | 1주 | 운영 루틴/문서/환경 정리 |
| Phase 1 | 2~3주 | 학생 MVP 동선 고정 |
| Phase 2 | 2~4주 | 관리자 운영 안정화 |
| Phase 3 | 1~2주 | 보호자 읽기 흐름 고정 |
| Phase 4 | 1~2주 | 교사 운영 핵심 정리 |
| Phase 5 | 2~3주 | 출석 시스템 도입 |
| Phase 6 | 2~4주 | 숙제 루프 도입 |
| Phase 7 | 1~2주 | 포인트/시간/패키지 정리 |
| Phase 8 | 2~4주 | 코스 보조(B) 도입 |
| Phase 9 | 3~6주 | 혼합형(C) 진입/안정화 |

운영 팁:
- 각 Phase 종료 시 28 서버 외부 테스트를 최소 1회 수행
- 실패/회귀가 있으면 다음 Phase 진입 전에 보정
